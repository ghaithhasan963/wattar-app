# خارطة تطوير Wattar

**الغرض:** تحويل المشروع الحالي إلى نسخة أولية اجتماعية قابلة للاختبار، ثم إلى منتج قابل للإطلاق عبر مراحل لها شروط قبول واضحة.
**الحالة:** خارطة عمل أولية؛ بعض تفاصيلها أصبحت تاريخية بعد دفعات التنفيذ والنشر اللاحقة. راجع تحديث الحالة أدناه قبل الاعتماد على الجداول وقوائم الانتظار.
**قاعدة العمل:** لا تُعد الميزة مكتملة لأن الشاشة موجودة أو لأن APK بُني؛ لا تُعتمد إلا بعد اختبار تدفقها من البداية إلى النهاية وتسجيل نتيجة الاختبار.

## تحديث الحالة — 2026-11-10

- طُبّقت ترحيلات المجتمع والاقتصاد ذي العملات الثلاث والمهمات وحضور الغرف وصلاحيات الوكلاء وبرنامج المضيفات على مشروع Supabase الإنتاجي، ونُشرت الدوال المطلوبة. فحوصات الدوال غير الموثقة أعادت `401` كما هو متوقع.
- نُشرت دالة `agent-phone-login`: يستطيع الوكيل النشط استخدام رقم الهاتف الدولي وكلمة المرور نفسها دون SMS. اجتاز فحص Deno وفحص أنواع لوحة الإدارة؛ اختُبر رفض رقم غير موجود وطلب CORS، لكن تسجيل الدخول بحساب وكيل فعلي لم يُختبر.
- آخر نسخة GitHub منشورة هي commit `02b9386`، وآخر بناء GitHub Actions ناجح هو [run 8](https://github.com/ghaithhasan963/wattar-app/actions/runs/42661277293). التغييرات الأحدث محلية حتى دفعها إلى `master`، والذي يشغّل بناء APK عبر GitHub Actions تلقائيًا؛ لا تستخدم EAS لهذا الإصدار.
- اجتازت التغييرات المحلية فحص أنواع تطبيق الهاتف، وتصدير Android، وبناء لوحة الإدارة، وفحص Deno لكل 26 دالة، وفحص `git diff --check`. اجتاز endpoint دخول الهاتف اختبار رفض رقم غير موجود وطلب CORS.
- هذه نسخة اختبار وليست إعلان جاهزية إطلاق تجاري. ما يزال الاختبار العملي بحساب وكيل حقيقي، وتسجيل/استعادة الحساب، والصوت بين جهازين، وPush على جهاز مستلم مطلوبًا. زر Facebook يعرض عدم التوفر كما طُلب؛ SMS للمستخدمين وKYC ليسا ضمن الخدمات المهيأة.

## 1. ملخص تنفيذي

المشروع ليس صفحة فارغة: يوجد تطبيق Android/iOS مبني بـ Expo وReact Native، وخدمات خلفية على Supabase، وEdge Functions، ولوحة إدارة ويب. لكنه ليس جاهزًا للإطلاق التجاري. أهم ما يمنع ذلك الآن هو عدم إثبات التسجيل والصوت على بيئة حقيقية، وعدم وجود مصفوفة اختبارات موثقة، ووجود فجوات بين بعض الواجهات والخادم ولوحة الإدارة.

**الترتيب المعتمد:**

1. تثبيت خط أساس قابل لإعادة الاختبار وفحص إعدادات الخدمات.
2. إصلاح المصادقة وإثبات التسجيل والدخول والاستعادة على حسابات حقيقية.
3. إصلاح الغرف والصوت وإثبات اتصال مستخدمين فعليين على جهازين.
4. إكمال الحد الأدنى من المجتمع والسلامة والإدارة.
5. اختبار الاعتمادية والأداء والتوافق على مجموعة أجهزة.
6. دراسة اقتصاد افتراضي آمن ومراجعة متطلبات المتاجر والقانون قبل أي بيع أو سحب أموال.
7. إطلاق تدريجي ومراقبة ثم توسع.

**لا نعيد بناء الواجهات أو نطلب APK جديدًا كحل لمشكلة وظيفية** قبل تحديد سبب المشكلة وإصلاحه واختباره. تغييرات JavaScript وحدها لا تصلح خدمة خلفية غير منشورة أو سرًا غير مضبوط.

## 2. نطاق المنتج والقرارات الحالية

- السوق الأول: المستخدمون العرب؛ الواجهة عربية وRTL أولًا.
- المنصة الأولى: Android، مع إبقاء بنية iOS قابلة للبناء.
- الهدف الأول: نسخة اجتماعية أساسية تعمل فعليًا، لا إطلاق كل أنظمة الربح دفعة واحدة.
- النسخة الأولية: التسجيل، الملف الشخصي، الأصدقاء والرسائل، الغرف العامة/الخاصة، الصوت، الإبلاغ والحظر، ولوحة تشغيل أساسية.
- الألعاب في النسخة الأولية تكون للتفاعل المجاني فقط إلى أن يُحسم نموذجها ومراجعتها.
- لا تُفعّل مشتريات أو تحويلات نقدية أو سحب أرباح حقيقية في بيئة الإنتاج قبل موافقة منفصلة على التصميم القانوني والتجاري والأمني.
- «يعمل على كل الهواتف» ليس وعدًا قابلًا للإثبات. سنحدد حدًا أدنى معلنًا، ثم نختبر قائمة أجهزة وأنظمة فعلية ونوثق الاستثناءات.

## 3. لقطة الحالة الراهنة من مراجعة الملفات

هذه نتائج مراجعة ثابتة للمصدر، وليست إثباتًا لحالة الخدمات المنشورة:

| المجال | الموجود في المشروع | ما لم يثبت بعد / الفجوة |
|---|---|---|
| تطبيق الهاتف | Expo/React Native، مسارات تسجيل، تبويبات، غرف، رسائل وألعاب | لا توجد في حزمة التطبيق أوامر اختبار مؤتمتة ظاهرة؛ نجاح التجميع لا يثبت نجاح الوظائف على جهاز |
| المصادقة | شاشات بريد/كلمة مرور وهاتف وGoogle وFacebook وزائر، وربط جلسة Supabase | نجاحها يتطلب ضبط المزودين والروابط وSMS/البريد في Supabase واختبار الرجوع للتطبيق. هذه الإعدادات غير قابلة للتحقق من المصدر |
| الملف الشخصي | جلب الملف وتعديله، وتوجد دالة/مشغّل SQL لإنشاء ملفات Auth | يجب اختبار إنشاء الحساب، التأكيد، أول تحميل للملف، وسياسات RLS على المشروع الفعلي |
| الصوت | عميل LiveKit ودالة إصدار رمز | الدالة تعيد `LIVEKIT_NOT_CONFIGURED` عند غياب الأسرار. لم يُثبت الاتصال أو نشر صوت من جهازين |
| الغرف | إنشاء غرفة، مقاعد، رسائل، ودعوات/تحديثات في SQL patches | يجب التأكد من نشر كل التعديلات والدوال على نفس مشروع Supabase. كلمة مرور الغرفة تُرسل ضمن إنشاء الغرفة وتُخزن في حقل قاعدة البيانات؛ يلزم استبدال هذا المسار بتصميم خاص آمن قبل الاعتماد على الغرف المحمية بكلمة مرور |
| الاقتصاد | جداول معاملات ودالة SQL لتحديث الرصيد ذريًا بمفتاح منع التكرار، ودوال مالية وألعاب | وجود ledger لا يثبت أن جميع المسارات تستخدمه بأمان. توجد مسارات شحن/سحب ورهان حالية، ولا تُطلق قبل تدقيق شامل وموافقة المنتج |
| لوحة الإدارة | دخول محمي بالجلسة وصفحات للمستخدمين والغرف والألعاب والوكلاء والشحن والسحب والإعدادات والتحويلات | لا تظهر صفحات تشغيل مخصصة للبلاغات والعقوبات والهدايا والاشتراكات والمشتريات والإعلانات والإشعارات والتدقيق التحليلي الشامل |
| التوافق | إعداد Expo يحدد Android 7.0 / API 24 حدًا أدنى، وبناء الاختبار يستخدم معماريات Android الافتراضية | لم يُختبر على مجموعة أجهزة؛ توسيع ABI لا يضمن وحده التوافق أو عمل الصوت على كل مصنع |
| التوثيق | مخطط SQL وملفات patches ودليل تشغيل | يلزم اعتماد ترتيب ترحيلات واحد وتحديث التوثيق بعد التحقق الفعلي، لا افتراض أن الملفات طُبقت على الخادم |

### نتيجة تحقق إعداد المصادقة (2026-11-07)

تم فحص نقطة إعدادات Supabase العامة للمشروع الذي يشير إليه ملف بيئة التطبيق، دون إنشاء مستخدم أو كشف أي مفتاح:

- Email: مفعّل على مستوى المزود.
- Phone/SMS: غير مفعّل.
- Google OAuth: غير مفعّل.
- Facebook OAuth: غير مفعّل.

هذا الفحص يثبت حالة تفعيل المزود فقط، ولا يثبت إعداد SMTP أو تأكيد البريد أو بيانات Client ID/Secret أو روابط Redirect URLs أو نجاح رحلة التسجيل. يجب تفعيل المزودين المطلوبين وضبط بياناتهم من لوحة Supabase ومزود الهوية قبل اختبارهم؛ لا توضع الأسرار داخل التطبيق أو المحادثة. لم يتم التحقق من إعداد LiveKit أو تشغيل SQL patches على المشروع البعيد.

## 4. مراحل التنفيذ وبوابات القبول

### المرحلة 0 — خط الأساس وتشخيص الخدمات (P0)

**الهدف:** معرفة ما يعمل وما لا يعمل على البيئة الحالية قبل تغيير الشيفرة.

**التنفيذ:**
- تثبيت معرفات البيئات: Development / Test / Production، والتأكد من أن التطبيق ولوحة الإدارة والخدمات تشير إلى مشروع Supabase المقصود.
- فحص إصدارات المخطط وملفات SQL المطبقة، وسياسات RLS، وRealtime، وحاويات Storage، وحالة نشر Edge Functions.
- إعداد قائمة تحقق لا تحتوي على أسرار: حالة Google/Facebook/Email/Phone، روابط إعادة التوجيه، إعداد SMS والبريد، وأسرار LiveKit الموجودة من عدمها. لا تُرسل مفاتيح أو أسرار في المحادثة.
- إعادة إنتاج مشكلتي التسجيل والصوت وتسجيل الرسالة الظاهرة وسجلات الخطأ ووقت التجربة وإصدار التطبيق.
- اعتماد خطة اختبار على Android فعلي ومحاكي، وتسجيل نوع الجهاز وإصدار النظام والمعمارية لكل نتيجة.

**بوابة القبول:**
- سجل بيئة يبين لكل خدمة: مضبوط/غير مضبوط/غير معروف، دون كشف أسرار.
- خطوات إعادة إنتاج موثقة لكل عطل حالي.
- لا توجد migrations تُنفذ على قاعدة بيانات إنتاجية خلال التشخيص.

**المطلوب من صاحب المشروع:** تأكيد حالة الإعداد من لوحة Supabase وLiveKit (نعم/لا فقط) أو تنفيذ خطوات تحقق موجهة؛ لا تشارك كلمات مرور أو مفاتيح API.

### المرحلة 1 — المصادقة والحساب (P0)

**الهدف:** جعل إنشاء الحساب والدخول والاستعادة موثوقة قبل اختبار بقية الرحلات.

**التدفقات:**
- إنشاء حساب بريد جديد، التأكيد إن كان مطلوبًا، ثم تسجيل الدخول والخروج.
- إعادة ضبط كلمة المرور، انتهاء الجلسة وتجديدها، وإعادة فتح التطبيق.
- تسجيل الهاتف ورمز SMS عند توفير مزود ورسوم/اعتمادات الإرسال.
- Google وFacebook بعد إعداد تطبيقات المزودين وRedirect URLs في Supabase.
- إنشاء ملف مستخدم واحد لكل حساب، وتحديث الصورة والاسم والاسم الفريد.
- عرض رسائل خطأ صريحة للمستخدم بدل حالات نجاح صامتة.

**بوابة القبول:**
- اجتياز كل تدفق مفعّل على Android حقيقي من البداية إلى النهاية بحساب جديد وحساب موجود.
- لا يتكرر ملف `users` ولا يبقى المستخدم عالقًا بين شاشة التأكيد والواجهة.
- يعمل الخروج، إعادة فتح التطبيق واستعادة الجلسة، وتظهر أخطاء الشبكة/الإعداد بوضوح.
- توثيق أي مزود غير مفعّل باعتباره غير متاح بدل عرض زر يوحي بأنه يعمل.

### المرحلة 2 — الغرف والصوت الحي (P0)

**الهدف:** إثبات اتصال صوتي ثنائي الاتجاه، وليس الاكتفاء بإنشاء غرفة أو إصدار token.

**التنفيذ:**
- التحقق من نشر `livekit-token` وضبط إعدادات LiveKit على الخادم فقط.
- توحيد هوية الغرفة بين قاعدة البيانات وخادم الصوت؛ وعدم تخزين أو كشف أسرار LiveKit في التطبيق.
- مراجعة صلاحية token: المستخدم، حالة الغرفة، الدعوة/الخصوصية، مدة الصلاحية، حدود الطلبات، وصلاحيات النشر/الاستماع.
- تعريف مصدر موثوق واحد لحالة المقعد والمتحدث والمستمع والكتم؛ ومزامنته مع اتصال LiveKit عند الدخول والخروج والانقطاع.
- إصلاح إنشاء الغرفة الخاصة: عدم تخزين كلمة مرور صريحة. اعتماد دعوات وصلاحيات خادمية، أو تصميم آمن مُراجع قبل الإبقاء على كلمة مرور.
- اختبار طلب إذن الميكروفون، رفض الإذن، إعادة المحاولة من إعدادات النظام، تبديل الشبكة، الخلفية/العودة، دخول وخروج متكرر، وإنهاء التطبيق المفاجئ.
- إضافة حالات اتصال واضحة للمستخدم: جارٍ الاتصال، متصل، إعادة الاتصال، الصوت غير مهيأ، وفشل مع إجراء مقترح.

**بوابة القبول:**
- جهازان بحسابين مختلفين يدخلان الغرفة نفسها ويسمع كل منهما الآخر ويتكلم بعد أخذ المقعد والإذن.
- يظل الميكروفون مكتومًا حتى يفعّله المستخدم، ويتوقف النشر فعليًا عند الكتم والخروج.
- فشل الخدمة أو الشبكة لا يعرض نجاحًا كاذبًا ولا يترك مقعدًا/حضورًا عالقًا.
- اختبارات متكررة للدخول والخروج وإعادة الاتصال على أكثر من جهاز Android.

### المرحلة 3 — المجتمع والسلامة الأساسية (P1)

**الهدف:** إكمال التجربة الاجتماعية اليومية والحد الأدنى من حماية المستخدمين.

**النطاق:** البحث عن مستخدم، طلبات وقبول الصداقة، المحادثات الخاصة، الدعوات، الإشعارات، حالة النشاط، الحظر، الإبلاغ، وسياسات المحتوى والحد من الإزعاج.

**بوابة القبول:**
- اختبار بحسابين على جهازين لكل مسار أساسي مع Realtime، ثم اختبار عند انقطاع الإنترنت والعودة.
- الحظر يمنع التفاعل المقصود وفق سياسة واضحة؛ والإبلاغ يصل للمشرفين مع حالة معالجة.
- لا يستطيع مستخدم قراءة محادثة أو دعوة أو تقرير لا يخصه.
- الإشعارات اختيارية وتعمل بعد إعداد الاعتمادات؛ رفضها لا يعطل بقية التطبيق.

### المرحلة 4 — لوحة الإدارة والتشغيل (P1)

**الهدف:** تمكين الإدارة الآمنة اليومية، لا مجرد تسجيل دخول للوحة.

**النطاق الأول:** البحث وإدارة الحسابات والحالات، إدارة الغرف، مراجعة البلاغات، العقوبات والاستئناف، إدارة الهدايا/المحتوى، الإعلانات والإشعارات، سجل التدقيق، مؤشرات الاستخدام والأعطال.

**متطلبات الأمان:**
- الصلاحيات تُفرض في قاعدة البيانات وEdge Functions، لا في إخفاء عناصر الواجهة فقط.
- فصل أدوار الدعم والإشراف والمالية ومدير النظام بمبدأ أقل صلاحية.
- تسجيل كل إجراء حساس: المنفّذ، السبب، الكيان، الوقت، والتغيير قبل/بعد.
- تأكيد إضافي للعمليات الخطرة، مع منع تعديل الأرصدة يدويًا خارج مسار مالي مسجل.

**بوابة القبول:**
- اختبارات السماح/الرفض لكل دور على الواجهة والخادم وRLS.
- كل قرار إشرافي حساس يظهر في سجل تدقيق قابل للمراجعة.
- تجربة كاملة لموظف دعم ومشرف ومدير نظام بحسابات منفصلة.

### المرحلة 5 — التصميم وتجربة الاستخدام (P1، بالتوازي بعد تثبيت التدفقات)

**الهدف:** تحسين الهوية والسهولة دون بناء واجهات شكلية أو تأخير إصلاح الوظائف.

**التنفيذ:** دراسة منافسين موثقة لرحلات الدخول والغرف والاكتشاف والاحتفاظ والسلامة؛ خريطة تنقل؛ نماذج أولية عربية RTL؛ حالات التحميل والفراغ والخطأ والاتصال الضعيف؛ مراجعة التباين وإمكانية الوصول؛ اختبار قابلية استخدام مع مستخدمين عرب.

**بوابة القبول:**
- مراجعة واعتماد التصميم قبل تطبيقه على الشاشات.
- كل عنصر تفاعلي موصول بفعل حقيقي، أو يظهر بوضوح أنه غير متاح.
- نجاح المستخدمين التجريبيين في إكمال المهام الأساسية دون توجيه مباشر؛ تُسجل المشاكل قبل التجميل الإضافي.

### المرحلة 6 — الاختبار والتوافق والأداء (P1)

**الهدف:** قياس الاستقرار ضمن نطاق أجهزة معلن.

**مصفوفة البداية المقترحة:** Android API 24 كحد أدنى للمشروع، ثم أجهزة فعلية منخفضة ومتوسطة وحديثة، ومعماريات ARM 32/64 حيث تتوفر أجهزة مدعومة، ومحاكي x86_64. تُضاف أجهزة iOS في مسار مستقل قبل نشر iOS.

**الاختبارات:** فتح بارد، تسجيل/خروج، تبديل الشبكة، رسائل متزامنة، غرف متعددة، أذونات، استهلاك الذاكرة/البطارية/البيانات، اختبار مدة مكالمة، وتعطل التطبيق.

**بوابة القبول:**
- قائمة أجهزة فعلية ونتائج مؤرخة، مع توثيق الأجهزة غير المدعومة.
- لا أعطال حرجة معروفة في التدفقات الأساسية، ولا فشل متكرر في الاتصال أو فقدان بيانات.
- تعريف مؤشرات أداء قبل التوسع (زمن فتح التطبيق، زمن الدخول للغرفة، نجاح الاتصال، وصول الرسائل، الأعطال).

### المرحلة 7 — الاقتصاد الافتراضي والربح (P2، موافقة منفصلة)

**الهدف:** تصميم نظام اقتصادي قابل للمراجعة قبل إتاحة أي شراء أو استرداد قيمة.

**قبل البرمجة التجارية:**
- تحديد ملكية العملات، هل لها قيمة نقدية، أهلية المضيفين، شروط السحب، العمولة، الضرائب، الدول المدعومة، التحقق من الهوية، الاحتيال والاسترداد.
- مقارنة طرق الشراء المسموح بها في Google Play والأسواق المستهدفة، والتحقق قانونيًا من عمليات الدفع والتحويل والسحب؛ القواعد تختلف حسب البلد وتتغير.
- إعداد نموذج تكلفة واقعي: الصوت، التخزين، الإشعارات، معالجة الدفع، الدعم، والرسوم. «ميزانية صفر» لا تضمن تشغيلًا تجاريًا مجانيًا.
- اعتماد سياسة واضحة للألعاب؛ لا تُعرض ألعاب رهان على أموال أو أرصدة قابلة للتحويل قبل مراجعة قانونية وسياسات المتاجر.

**التصميم التقني عند الموافقة:** سجل قيود مزدوج/متوازن أو نموذج محاسبي معتمد، معرفات idempotency، تحقق إيصالات الشراء خادميًا، معالجة webhook قابلة لإعادة المحاولة، تسويات ومطابقة، سجل تغييرات، حدود ومكافحة إساءة الاستخدام، وخطة ردّ الأموال.

**بوابة القبول:**
- مراجعة مستقلة للمخطط المالي ومسارات كل Edge Function وRLS.
- اختبارات تكرار الطلبات وسباق العمليات والاسترداد والتسوية والرفض.
- لا مفتاح شراء أو تسعير أو صرف حقيقي في الإنتاج قبل موافقة صاحب المنتج على الشروط ومراجعة المتطلبات القانونية ومتاجر التطبيقات.

### المرحلة 8 — الإطلاق التدريجي (P2)

**الهدف:** إطلاق محدود يمكن إيقافه أو التراجع عنه.

**التنفيذ:** مجموعة مغلقة، شروط استخدام وخصوصية ودعم وإبلاغ، مراقبة الأخطاء والاتصال، نسخ احتياطي واختبار استعادة، خطة استجابة للحوادث، مفاتيح منفصلة لكل بيئة، وخطة Rollback للإصدار والخدمات.

**بوابة القبول:** قائمة إطلاق موقعة، نتائج الاختبارات، مسؤول دعم، مؤشرات إنذار، وتجربة عملية لاستعادة نسخة احتياطية والرجوع عن إصدار.

## 6. ما لن نفعله الآن

- لن نطلب APK جديدًا لمجرد أن APK السابق لم يصلح تسجيلًا أو صوتًا؛ سنبني بعد إصلاح السبب فقط.
- لن نعد بدعم كل هاتف دون تحديد حد أدنى ومصفوفة أجهزة.
- لن نفعّل الشحن أو السحب أو رهان الألعاب أو تحويل أرباح حقيقية قبل اعتماد النموذج التجاري والقانوني واختبارات الأمان.
- لن نغيّر قاعدة البيانات المنشورة أو بيانات المستخدمين خلال التشخيص دون موافقة صريحة وخطة تراجع.
- لن نعتبر مزود تسجيل دخول متاحًا قبل اختباره من جهاز إلى Supabase والعودة إلى التطبيق.

## 7. أول دفعة عمل بعد اعتماد الخارطة

1. تنفيذ المرحلة 0 فقط: جرد حالة الإعداد والنشر والتعديلات المطبقة دون تعديل بيانات الإنتاج.
2. إعادة إنتاج التسجيل والصوت وجمع أخطاء منقحة.
3. تقرير قصير: السبب الجذري لكل عطل، الإعداد الخارجي المطلوب، الملفات التي ستتغير، واختبار القبول.
4. بعد موافقة صاحب المشروع على نطاق الإصلاح، تنفيذ المرحلة 1 ثم 2 على دفعات صغيرة.
5. لا يصدر APK جديد إلا بعد اجتياز شروط قبول الدفعة التي يحتويها.

## 8. المعلومات المطلوبة من صاحب المشروع

لا ترسل أسرارًا أو كلمات مرور. عند بدء المرحلة 0 نحتاج إجابات نعم/لا أو حالة فقط:

- هل Google وFacebook وEmail وPhone مفعلة في Authentication لدى Supabase؟
- هل أُضيف رابط `wattar://callback` وروابط التأكيد/الاستعادة إلى قائمة Redirect URLs؟
- هل نُشرت دالة `livekit-token` على نفس مشروع Supabase الذي يستخدمه التطبيق؟
- هل أُضيفت أسرار LiveKit في Edge Function Secrets؟ لا ترسل قيمها.
- ما نسخة Android ورقم الطراز اللذان ظهر عليهما الفشل، وما نص الخطأ أو لقطة منقحة؟
- هل نبدأ بتثبيت المصادقة والصوت أولًا (الموصى به)، مع إبقاء الاقتصاد المالي خارج التنفيذ حاليًا؟

## 9. تعريف اكتمال المنتج
