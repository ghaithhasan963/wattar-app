# WATTAR — MASTER PROJECT DEVELOPMENT & ENGINEERING PROMPT

## 1. دورك ومهمتك

أنت تعمل بصفتك فريقاً هندسياً متكاملاً يضم:

- Principal Software Architect.
- Senior React Native / Expo Engineer.
- Senior React / TypeScript Engineer.
- Supabase / PostgreSQL Backend Engineer.
- LiveKit Real-time Audio Engineer.
- UI/UX & Motion Design Specialist.
- Security Engineer.
- QA Automation & Performance Engineer.
- DevOps / Infrastructure Engineer.

مهمتك هي استكمال وتطوير مشروع Wattar الموجود بالفعل، وتحويله إلى منصة اجتماعية صوتية احترافية بمستوى التطبيقات العالمية المشابهة لـ BIGO LIVE، مع هوية مستقلة وتصميم أكثر تميزاً.

**لا تبدأ بإنشاء مشروع جديد ولا تعِد كتابة المشروع الحالي من الصفر.**

المشروع يحتوي على أكثر من 500 ملف وأكثر من 100,000 سطر برمجي، ويضم تطبيقاً وقاعدة بيانات وخدمات خلفية ولوحات إدارة.

المشكلة الحالية أن أجزاء من التطبيق بدائية، والتصميم غير احترافي، وبعض الوظائف غير مكتملة أو لا تعمل بالشكل الصحيح، والمؤثرات البصرية ضعيفة.

المطلوب هو فهم المشروع كاملاً، وتقييمه، ثم إصلاحه واستكماله وتطويره.

# 2. قواعد العمل الأساسية

1. افحص المشروع بالكامل قبل إجراء أي تعديل.
2. افهم البنية الحالية وقاعدة البيانات والعلاقات والوظائف الموجودة.
3. لا تحذف وظيفة موجودة قبل فهمها والتأكد من عدم اعتماد أجزاء أخرى عليها.
4. لا تنشئ أنظمة مكررة إذا كان هناك نظام قائم يمكن تطويره.
5. لا تستخدم بيانات وهمية أو Mockups بدلاً من الوظائف الحقيقية.
6. لا تعتبر الوظيفة مكتملة لمجرد ظهور واجهتها.
7. اربط جميع الواجهات بالخلفية وقاعدة البيانات بصورة صحيحة.
8. أصلح الأخطاء الموجودة قبل إضافة تعقيدات جديدة.
9. حافظ على التقنيات الحالية ما دامت مناسبة.
10. لا تغيّر بنية المشروع جذرياً دون سبب تقني موثق.
11. لا تكشف مفاتيح API أو كلمات المرور أو أسرار الخادم.
12. لا تضع أي مفاتيح خاصة أو بيانات حساسة داخل تطبيق الهاتف.
13. لا تنفذ تعديلات مالية مباشرة على الإنتاج أثناء الاختبار.
14. لا تنفذ عمليات نشر أو تغييرات حساسة دون موافقة صريحة.
15. لا تدّعِ نجاح اختبار لم يتم تنفيذه فعلياً.

إذا واجهت قراراً غير محسوم في المواصفات، افحص النظام الحالي أولاً، ثم اقترح الحل الأكثر أماناً وقابلية للتوسع، ووثّق القرار قبل تنفيذه إذا كان يؤثر على الأموال أو الأمان أو بنية قاعدة البيانات.

# 11. نظام العملات والمحافظ

هناك عملتان أساسيتان فقط:

## Coin

- عملة يتم شحنها مقابل أموال حقيقية.
- تستخدم للهدايا.
- تستخدم للألعاب.
- تستخدم للشراء داخل التطبيق.
- لا يمكن سحبها نقداً.
- أرباح الألعاب تعود Coin فقط.
- لا يمكن تحويل Coin إلى Diamond.

## Diamond

- عملة أرباح للمضيفات المعتمدات والموثقات فقط.
- المستخدم العادي لا يحصل على Diamond.
- حتى إذا فتح المستخدم العادي غرفة واستقبل هدايا، يحصل على Coin وليس Diamond.
- المضيفة المعتمدة تحصل على Diamond وفق عقدها ونسبة الأرباح المحددة لها.
- Diamond يمكن أن يكون مؤهلاً للسحب أو للتحويل إلى Coin وفق قواعد الإدارة.

يجب الفصل بين:

- Diamond القابل للسحب.
- Diamond غير القابل للسحب إن وجدت هذه الفئة.
- Coin المتاح.
- Coin المحجوز.
- أرصدة الوكلاء.
- أرصدة التمويل التشغيلي.

لا تسمح بتحويل Coin إلى Diamond.

## الإدارة المالية

الإدارة تتحكم في:

- أسعار Coin.
- باقات الشحن.
- أسعار الهدايا.
- نسب تحويل الهدايا إلى Diamond.
- أسعار تحويل Diamond.
- عمولات المنصة.
- عمولات الوكالات.
- عمولات الوكلاء.
- حدود السحب.
- رسوم السحب.
- المكافآت.

جميع الأسعار والنسب قابلة للتعديل.

أي تغيير جديد يطبق على العمليات المستقبلية فقط.

لا تغير أي معاملة مالية تاريخية عند تعديل النسب.

إذا كان مكلفاً أو معقداً، استخدم طلب شحن تتم مراجعته والموافقة عليه من الإدارة.

- TRC20.
- BEP20.

- الحد الأدنى.
- الحد الأعلى.
- الرسوم.
- الشبكات المتاحة.
- طرق الدفع.
- الدول المسموحة.

## طلبات الشحن والسحب

الإدارة تستطيع:

- قبوله.
- رفضه.
- طلب معلومات إضافية.
- تنفيذ العملية.
- تسجيل سبب الرفض.

حالات الطلب:

- Pending.
- Under Review.
- Approved.
- Rejected.
- Processing.
- Completed.
- Failed.

## الوكلاء

الوكيل ينفذ عمليات الشحن والسحب للمستخدمين التابعين له مباشرة من محفظته التشغيلية.

لا يحتاج كل طلب من مستخدميه إلى موافقة الإدارة.

التوقع الأولي:

- حوالي 1,000 مستخدم مسجل خلال أول ثلاثة أشهر.
- تصميم أولي لاستيعاب 100 مستخدم متزامن.
- إمكانية حدوث ارتفاعات مفاجئة في عدد المستخدمين.

لا تشترِ موارد ضخمة مسبقاً.

صمم بنية قابلة للتوسع أفقياً.

افحص:

- Supabase Limits.
- LiveKit.
- Edge Functions.
- Database Connections.
- Realtime Connections.
- Storage.
- Bandwidth.
- CDN.
- Background Jobs.

أضف:

- Monitoring.
- Logging.
- Error Tracking.
- Load Balancing عند الحاجة.
- Rate Limiting.
- Health Checks.
- Backups.
- Restore Procedures.

## LiveKit

قارن بين:

1. LiveKit Cloud.
2. Self-hosted LiveKit.

المطلوب اختيار أقل حل تكلفة بصورة واقعية مع مراعاة:

- الخادم.
- نقل البيانات.
- عدد المشاركين.
- جودة الصوت.
- الصيانة.
- التوسع.
- المراقبة.

لا تفترض أن Self-hosted مجاني.

لا تغيّر الخدمة الحالية قبل مقارنة فعلية واختبار.

# 28. العائلات وتحديات PK — مؤجلة

لا تنفذ نظام العائلات في الإصدار الأول.

لا تنفذ:

- إنشاء العائلات.
- عضوية العائلات.
- ترتيب العائلات.
- مكافآت العائلات.
- محافظ العائلات.

نظام العائلات مؤجل بالكامل إلى مرحلة مستقبلية.

كذلك تحديات PK مؤجلة، لأنها مرتبطة بنمط بث الفيديو في التطبيقات المشابهة.

لا تضف أي بث فيديو أو مكالمات فيديو أو وظائف فيديو في الإصدار الأول.

يجب ألا تعتمد الأنظمة الحالية على هذه الوظائف المؤجلة.

# 29. الاختبارات والجودة

لا تعتبر العمل مكتملاً دون اختبارات فعلية.

نفّذ:

## Unit Tests
للدوال والحسابات والمنطق المالي والصلاحيات.

## Integration Tests
للاتصال بين التطبيق والخلفية وقاعدة البيانات.

## E2E Tests
للتدفقات الأساسية.

## Security Tests
لـ RLS وAuth وLedger والصلاحيات وواجهات API.

## Load Tests
للصالات الصوتية والاتصالات وقاعدة البيانات.

## Performance Tests
للحركة والرسوم والصور والذاكرة.

## Financial Tests
لاختبار الشحن والسحب والهدايا والعمولات ومنع الازدواجية.

اختبر سيناريوهات مثل:

- إرسال هدية.
- خصم Coin.
- احتساب Diamond.
- تنفيذ عملية شحن.
- تنفيذ عملية سحب.
- انقطاع الاتصال أثناء العملية.
- إعادة إرسال الطلب نفسه.
- محاولة تنفيذ عملية دون رصيد كافٍ.
- محاولة مستخدم تعديل رصيد مستخدم آخر.
- محاولة وكيل الوصول إلى بيانات وكالة أخرى.
- محاولة مستخدم عادي الحصول على Diamond.
- محاولة مستخدم تجاوز حدود VIP.
